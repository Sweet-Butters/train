# 방향 결정 1 — 병목이 한 줄로 섰다 (2026-09-09, 코디네이터)

`docs/CONTRACT.md` 는 트랙의 경계를 정한다. 이 문서는 그 트랙들이 **무엇을 향해**
가는지를 정한다. 둘이 어긋나면 이 문서가 이긴다 - 경계는 목표를 위해 있다.

## 지금 서 있는 자리

부품은 넷 다 섰다. B 는 PDF 벡터·PPT 도형에서 구조를 오려내고, C 는 이름을 찾고,
A 는 인식기 둘을 프로세스 너머로 함께 세웠고, D 는 재는 장치를 만들었다.
그리고 그 장치를 실제 강의자료에 처음 대봤을 때 **판정률 0%** 가 나왔다.

D 의 실측 2건(`bench/README.md`)이 문제를 다시 정의했다. 우리가 못하는 것은
구조 인식이 아니다.

| 실측이 말한 것 | 어디 문제인가 |
|---|---|
| 이름이 픽셀 안에 있다 (텍스트 레이어 0자) | 입력단 - 텍스트가 아예 없다 |
| '그림' 이 슬라이드 통째다 | 입력단 - 오릴 자리를 못 찾는다 |
| 그림 371건 중 구조식은 두세 개, 나머지는 클립아트 | 입력단 - 무엇을 먹일지 안 고른다 |
| 인식기 하나로는 방어가 뚫린다 (오탐률 22%) | A - 합의 게이트가 엔진 둘부터 작동한다 |

넷 다 **입력단과 인식기** 문제다. C 의 이름 해석은 이미 병목이 아니다.
그러므로 네 트랙이 동시에 나아가는 국면은 끝났다. 병목이 한 줄로 서 있다:

    A 분할기 → B 배선 → D 실측

## 결정

### 1. A 는 통합 브랜치에서 나온다

지금 base 워크트리(`D:/orca/workspaces/train/chemcheck`)에 A 의 미커밋 작업이
얹혀 있다 - `bridge.py`, `segment.py`, `scripts/segment_worker.py`,
`scripts/setup_segmentation.sh`, `tests/test_segment.py`, `ocsr.py` 개편. 그리고
`tests/test_segment.py` 1 건이 깨진 상태다 (58 통과 / 1 실패).

통합 지점이 동시에 한 트랙의 작업대이면 통합이 그 트랙의 진행에 인질로 잡힌다.
지금 base 를 머지하려면 A 의 반쯤 된 작업을 커밋하거나 버려야 한다. 둘 다 나쁘다.

`Sweet-Butters/track-a-ocsr` 워크트리를 만들어 두었다. A 는 자기 변경을 그리로
옮기고, base 워크트리를 깨끗하게 되돌린다. **base 는 코디네이터의 문서와 머지만
받는다.**

### 2. `chemcheck/bridge.py` 는 소유자 없는 베이스 인프라

`scripts/setup_lite.sh` 와 같은 성격이다. 프로세스 너머 워커를 쓰는 곳이 이미
둘(OCSR, 분할기)이고 OCR 이 오면 셋이 된다. 소유자를 한 트랙에 두면 나머지가
우회로를 만든다 - `setup_*.sh` 와일드카드에서 이미 한 번 겪었다.

A 는 옮기기 전에 `bridge.py` 만 base 에 단독 커밋한다. 이후 변경은 코디네이터를
거친다.

### 3. `segment.py` 는 A 소유, `extract.py` 배선은 B

무거운 모델과 자체 venv(`.venv-seg`)를 쓰므로 A 다. 부르는 쪽은 `extract.py` 를
배타 소유한 B 다. 남의 파일을 대신 건드리지 않는다는 원칙 그대로다.

경계에 인터페이스를 하나 더 동결한다:

```python
# chemcheck/segment.py — A 가 유지, B 가 부른다
def available() -> bool: ...                 # 절대 예외를 올리지 않는다
def unavailable_reason() -> str | None: ...
def segment_page(page_image: Path, out_dir: Path) -> list[Path]: ...
```

**빈 목록이 정상이라는 것이 계약의 일부다.** 구조가 없는 페이지에서도, 분할기가
설치되지 않았을 때도 빈 목록이다. 이 셋만 유지되면 A 는 안을 마음대로 바꾼다.

### 4. '이게 구조식인가' 는 분할기의 산출물이다 — 크기 필터로 풀지 않는다

`extract.py` 의 필터는 크기뿐이고, 실측 2 에서 그것이 지배적 오탐원임이 드러났다.
아인슈타인 캐리커처에서 읽은 SMILES 가 슬라이드의 이름과 다르면 '오류' 가 되는데
자료는 멀쩡하다.

새 분류기를 만들지 않는다. 분할기가 구조 영역을 찾지 못한 페이지는 그림을 내지
않는다 - 그것이 게이트다.

따라오는 기본값 변경: **분할기가 없으면 래스터 페이지의 통이미지는 판정 대상에서
빠진다.** 지금은 통이미지를 인식기에 먹인다. 그 경로는 오탐만 낳는다. 빠진 그림은
조용히 사라지지 않고 '분할기 없음' 사유로 판정불가에 남는다 (B: 반환값, D: 리포트
문구).

### 5. 픽셀 속 이름(OCR)은 B 의 것이다 — 단 우선순위는 뒤

`extract.py` 의 책임은 '장에서 텍스트와 그림을 낸다' 다. 텍스트 레이어가 없으면
픽셀에서 만들어야 한다. C 는 텍스트를 **해석**한다 - 만들지 않는다.

다만 실측 2 의 398 장 덱은 텍스트가 100% 였다. 텍스트가 있는 자료가 먼저다.
OCR 은 P1 뒤쪽이다.

### 6. R 기 일반식과 반응 도식은 범위 밖이라고 못 박는다

실측 1 의 세 번째 원인이다. `OCN-R-NCO` 는 InChIKey 로 표현되지 않고 반응 도식은
단일 화합물이 아니다. 검사할 수 없는 것을 분모에 두면 판정률은 영원히 낮게 나오고
우리는 고칠 수 없는 숫자를 쫓는다.

README 에 비목표로 적는다. D 는 이것을 `NOT_A_STRUCTURE` 와 같은 급으로 다룬다 -
라벨 체계는 D 가 정한다.

### 7. 웹 브랜치(`origin/claude/repo-status-check-4vmkco`)는 머지하지 않는다

포크 이전 계보에서 갈라져 3 커밋 앞서 있다. 병합하면 5 파일이 충돌하고
(`extract.py`·`names.py`·`tests/test_pipeline.py`·`scripts/make_demo.py`·README)
동결된 `pipeline.py` 를 제 갈래로 끌고 온다. `offline_names.json` 은 C 의
`data/compounds.json` 과 같은 일을 두 번 한 것이다.

브랜치는 참고 자료로 남긴다. 값나가는 것만 소유 트랙이 다시 만든다:

# 방향 결정 3 — 숫자를 보기 전에 기준을 적는다 (2026-09-09 16:50, grill 결과)

## 1. 축소판을 지금 돌린다 (하루 끝이 아니라)

바뀐다: **10 분자 축소판 → 신호가 초록이면 50 분자 전체.** 이 숫자는 나머지 하루를 어디
쓸지를 바꾼다 - 두 엔진이 담합한다고 나오면 `recognize` 를 다듬는 일은 전부 헛일이다.
답을 바꾸는 측정은 먼저 한다.

정한다:

# 방향 결정 5 — 제품이 둘이라는 발견 (2026-09-09 17:35, grill 3 결과)

## 루프는 draw 의 우회로다 - 증명 두 줄

"LLM 이 구조를 내고 chemcheck 이 대조해 틀리면 정본으로 교체한다" 는 루프를 따라가면:

| 분기 | 루프의 출력 | draw 단독 |
|---|---|---|
| LLM 구조 == 정본 | LLM 구조(= 정본) | 정본 |
| LLM 구조 ≠ 정본 | 정본으로 교체 | 정본 |

두 분기 모두 같다. **루프 ≡ draw.** 남는 분기는 draw 가 실패했을 때뿐인데, 거기서 LLM 구조를
통과시키면 이 도구가 존재하는 이유가 사라진다. 그러므로 LLM 의 구조적 기여는 **0** 이다.

결론: 검증하지 말고 **만들지 않게 한다.** 루프가 아니라 툴콜이다.

    LLM: "아스피린을 그려줘" -> draw("aspirin") -> 정본 그림
                               (LLM 은 구조를 한 번도 만들지 않는다)

검증할 것을 만들지 않는 것이 검증하는 것보다 강하다. 검증기가 실패하는 모든 경로(미등재·범위 밖)
에서 검증 안 된 구조가 새어나갈 자리가, 툴콜에는 아예 없다. LLM 에게 남는 일 - **무엇을 그릴지
정하는 것** - 은 화학 능력이 아니라 문맥 능력이고, 틀려도 눈에 보인다. LLM 을 빼는 게 아니라
**위로 올린다. 호출자지 부품이 아니다.**

## 그래서 제품이 둘이다

| | **생성 시점** (draw 툴콜/웹) | **사후 검사** (recognize 합의) |
|---|---|---|
| 막는 것 | 틀린 구조가 **생기지 않게** | 이미 있는 그림을 검사 |
| 필요한 것 | PubChem/오프라인표 + RDKit | 엔진 둘 + 3GB + 합의 게이트 |
| 콜드스타트 / 메모리 / venv | ~0 / 수백MB / 1 | 200초 / 3GB / 2 |
| 측정된 성능 | 적중률 **98.5%** (588 표기) | 판정률 88%, 물러남 12% (n=50, 합성 상한) |
| 배포 | 오늘 가능 - 웹·플러그인·MCP 전부 | 서버 상주만 |
| **사람의 의심에 의존하나** | **아니오** | **예** |

마지막 줄이 핵심이다. README 가 지목한 문제는 *"틀렸다는 걸 아무도 모른 채 강의자료에 들어간다"*
였다. **사후 검사기는 사람이 의심해야 작동한다. 아무도 모르면 아무도 안 돌린다.** 생성 시점
대체는 그 의존을 없앤다.

**결정: 생성 시점이 제품이고 recognize 는 부속이다.** recognize 를 버리지 않는다 - 남이 만든
그림을 검사하는 유일한 길이라 값이 있다. 다만 오늘 하루를 무거운 쪽에 쓴 것이 맞았는지는 남긴다.

"루프" 라고 부르면 둘이 섞여서 recognize 의 3GB 가 툴콜 제품에 딸려온다. **이름을 갈라 부른다.**

## 범위 밖의 거절 계약 (R 기 일반식·반응 도식)

## 2. 그림은 틀렸다 - 메틸이 하나 많다

|---|---|---|
| MolScribe | `CN1C(=O)C2=C(N(C)C1=O)N(C)=CN2(C)C` - **RDKit 이 파싱 못 함**(5 가 질소) | 0.808 |

    DECIMER 가 읽은 것  InChIKey CSXLFNRQOLIQAN-UHFFFAOYSA-N   <- 골격부터 다르다

**그림이 자기 캡션과도 안 맞는다.** 이미지가 스스로 C8H10N4O2 라고 적어놨는데 메틸이 넷이면
C9H12N4O2 다. README 가 말한 문제의 교과서적 실례다 - 그럴듯하고, 캡션은 정확하고, 구조만 틀렸다.

### 설계 질문 - 파싱 실패는 침묵할 이유인가, 오류의 증거인가

`N(C)=CN2(C)C` 는 5 가 질소다. 이것은 **그릴 수 없는 분자**다. 인식기가 유효하지 않은 구조를
읽었다는 것은 두 가지 중 하나다:

1. 인식기가 못 읽었다 (잡음) - 지금의 해석
2. **그림이 화학적으로 불가능한 것을 그리고 있다** (증거)

이 경우는 2 다. 두 인식기가 **같은 방향으로**(N9 에 여분의 메틸) 어긋났기 때문이다. 서로 다른
답을 낸 것이 아니라 **같은 이상을 서로 다른 방식으로 표현**했다. 지금 설계는 그 정보를 버리고
'합의 실패' 로 뭉갠다.

가설이지 결론이 아니다 - 그림이 멀쩡한데 인식기가 원자가를 깨뜨리는 경우도 있을 수 있다.
**검증 방법**: 50 장 평가 세트에서 파싱 실패가 몇 건 났고, 그중 몇 건이 실제로 그림 문제였나.
D 의 로그에 이미 있다. 이것을 재기 전에는 규칙을 바꾸지 않는다.

# 방향 결정 6 — 도구는 답을 갖고 있었다 (2026-09-09 21:30, grill 4 결과)

## 1. 내 가설의 구멍에 해법이 있다 - InChIKey 가 아니라 **중원자 조성**

"두 엔진이 같은 방향으로 어긋났다" 는 판단은 내가 SMILES 문자열을 눈으로 읽고 한 **추론**이었다.
MolScribe 의 답은 파싱이 안 되니 InChIKey 가 없고, 비교할 물건이 아니었다.

그런데 같은 결론을 추론 없이 낼 수 있다. `MolFromSmiles(s, sanitize=False)` 는 **원자가 검사
없이** 그래프를 만든다. 5 가 질소여도 파싱된다. 거기서 원자를 센다:

| 출처 | 중원자 조성 |
|---|---|
| MolScribe (미검증 파싱) | **C9** N4 O2 |
| DECIMER (짝이온 제거) | **C9** N4 O2 |
| `draw("카페인")` 정본 | **C8** N4 O2 |
| **이미지가 스스로 인쇄한 화학식** | **C8** H10 N4 O2 |

**탄소 하나가 다르다. 원자를 세는 것은 추론이 아니다.**

- **중원자만 센다.** 암시적 수소는 원자가 규칙에서 나오는데 그게 깨진 상황이다.
- **일방향 신호다.** 조성이 다르면 구조가 다른 것이 확실하다. 같다고 구조가 같은 것은 아니다.
  '오류' 에는 쓰고 '일치' 에는 쓰지 않는다.
- **이미지에 인쇄된 화학식은 네 번째 독립 정보원**이다. 인식기와도, 이름과도 무관하다.

이번 케이스에서 **세 정보원(이름·인식기 둘·인쇄된 화학식)이 전부 "탄소 8 대 9" 를 가리켰는데
도구는 하나도 쓰지 않았다.**

## 2. 진짜 결함 - 합의 게이트가 이름 대조보다 앞에 있다

물러남 100% 는 "예상된 동작" 도 "도구가 쓸모없다" 도 아니다. **규칙을 잘못 골랐다는 뜻이다.**

가르는 기준: **물러남이 정보를 담고 있는가.** 담고 있지 않으면 사용자는 도구가 없었을 때와 같은
자리다. 이번 케이스는 **정보를 갖고도 안 줬다** - `draw("카페인")=RYYVLZVUVIJVGH` 와
`DECIMER=CSXLFNRQOLIQAN` 의 골격 비교는 이 프로젝트가 하는 바로 그 일인데, 도구가 계산해놓고
말하지 않았다.

**합의 게이트는 비교할 다른 정보원이 없을 때 쓰는 최후 수단이다.** 이번엔 이름이 있었다.

## 3. 판정이 이진인 것이 설계 결함이다

VERDICT 은 2-of-4 와 3-of-4 를 **다른 정밀도의 다른 등급**으로 냈다. chemcheck 은 "합의했다/
못했다" 둘뿐이라 확신의 정도가 다른 것들이 전부 같은 침묵으로 뭉개진다. 등급이 필요하다.

    관찰   MolScribe 파싱 실패(5가 질소) / DECIMER CSXLFNRQOLIQAN, 조성 C9N4O2
           이미지 인쇄 화학식 C8H10N4O2
    대조   이름 "카페인" 정본 RYYVLZVUVIJVGH, 조성 C8N4O2

    판정   이름과 그림이 다릅니다  [약]  (유효한 구조를 낸 인식기가 하나뿐이라 합의 확인 불가)

하루를 쓴 쪽이 침묵했고, 부속으로 내린 쪽이 답을 갖고 있었다.

## 정정 2 — OCR ≠ OCSR. 3GB 는 이미지 입력의 비용이 아니라 **검출의 비용**이다

내 문서가 이 둘을 뭉갰다.

| | 무엇을 읽나 | 비용 |
|---|---|---|
| **OCR** | 인쇄된 글자 "Caffeine" | 가볍다. 브라우저에서 가능 |
| **OCSR** | 그려진 구조 | 3GB · 200 초 · 서버 |

**서버 없는 웹 페이지가 이미지를 받을 수 있다**: 붙여넣기 → OCR 로 이름만 뽑기 →
오프라인 표/PubChem → RDKit.js → 정본 그림. 이미 만든 페이지에 **한 층만 얹으면 된다.**

포기하는 것은 **검출 하나**다 - "당신이 가진 그림이 틀렸다" 는 말. 그건 그림을 읽어야 하고,
그것이 OCSR 이다.

그래서 갈림은 "OCR 이냐 OCSR 이냐" 가 아니다:

> **사용자에게 정본을 주는 것으로 충분한가, 아니면 "당신이 가진 그림이 틀렸다"고
> 말해줘야 하는가.**

## 새 사실 — 실패 클래스가 둘이다

|  | 합성 50 장의 물러남 6 건 | Gemini 1 장 |
|---|---|---|
| 정답 구조가 존재하나 | **예** - RDKit 이 그렸으니까 | **아니오** - 그려진 것이 중성 분자로 존재할 수 없다 |
| 왜 물러났나 | 한 엔진이 틀렸다 (정답 낸 엔진이 있었다) | 어떤 엔진도 유효한 답을 못 낸다 |
| 세 번째 엔진이 회수하나 | 예 - 상한 100% | **아니오** |

**"물러남 6 건 전부 한 엔진만 틀림 → 세 번째 엔진 회수 상한 100%" 를 실제 자료에 적용하면
안 된다.** MolNexTR 을 붙여도 존재하지 않는 분자에 유효한 InChIKey 를 줄 수는 없다.

## 파싱 실패는 가설보다 **강한** 신호다

> "이 그림에 대해 유효한 답이 존재하지 않는다" - 그것은 인식기의 실패가 아니라
> **그림의 성질**이다.

그리고 그 판정에는 **두 엔진의 일치도, 이름도 필요 없다.** 한 엔진이 원자가를 깨뜨렸고 다른
엔진이 전하를 맞추려 짝이온을 지어냈다는 것 자체가 관찰이다. **지금 있는 판정 중 유일하게
이름 없이 낼 수 있는 오류 신호다.**

## 새 사실 1 — 이미지가 자기 정답을 텍스트로 들고 있다

전부 OCR 로 뽑히고, 인식기와 무관하며, **오늘 여섯 장에서 텍스트는 한 번도 틀리지 않았다.**

## 새 사실 2 — 모델마다 다른 화합물에서 틀린다

Gemini 는 카페인에서 틀리고 L-알라닌은 맞혔다. GPT 는 카페인을 맞히고 L-알라닌 입체가 의심스럽다.
**"어느 모델이 낫다" 가 아니라 "어느 모델도 믿을 수 없다" 다.** 그리고 이것이 왜 도구가 필요한지의
근거다 - 사용자는 어느 모델이 어느 화합물에서 틀릴지 미리 알 수 없다.

## 경고 — GPT L-알라닌 판정은 **내 눈이지 도구가 아니다**

NH2 가 굵은 쐐기(앞), H 가 빗금(뒤), CH3 왼쪽, COOH 오른쪽. 최저순위 H 가 뒤를 향하므로
NH2(12시) → COOH(3시) → CH3(9시) 를 그대로 읽으면 시계방향 = **R**. 라벨은 (2S).
**그러나 이것은 추론이고, 이 프로젝트는 사람의 눈을 판정에 두지 않기로 했다.**
도구로 확인하기 전까지 사실로 취급하지 않는다. (메모리 부족으로 아직 못 돌렸다.)

덧붙여 - 설령 도구가 확인해도 현재 규칙은 입체만 다르면 **'주의'** 로 내린다. '오류' 가 아니다.
입체가 LLM 오류의 9.3%(MolErr2Fix)이고 여기서 실제로 나왔다면, 그 규칙을 다시 봐야 한다.
