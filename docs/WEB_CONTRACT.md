# 웹 제품 병렬 작업 계약 (해커톤)

한 화면. 이미지를 붙여넣거나 이름을 치면, **정본은 항상 나오고** 그림을 읽을 수 있으면 대조까지 한다.
화면이 비는 경우가 없어야 한다 - 그것이 이 설계의 원칙이다.

    붙여넣기 ─┬─ [즉시·브라우저] 이름 -> 정본 그림·SMILES·InChIKey   (실패하지 않음)
              └─ [~20초·서버]    그림 -> 읽은 구조 -> 대조 -> 판정   (실패해도 위는 살아 있음)

## 파일 소유 — 배타적. 남의 파일은 열지 않는다

| 트랙 | 소유 파일 | 무거운 환경 |
|---|---|---|
| **U** 화면 | `web/index.html`, `web/app.js`, `web/style.css` | 없음 |
| **C** 크롭 | `web/crop.js` | 없음 |
| **O** OCR | `web/ocr.js` | 없음 |
| **S** 서버 | `server/` 전부 | 있음 (엔진 3GB) |
| 손대지 않음 | `web/build_table.py`, `web/compounds.js` (B 가 구움), `chemcheck/**` | |

## 동결 인터페이스 — 커밋 뒤 바꾸지 않는다. 바꿔야 하면 코디네이터에게 올린다

```js
// web/crop.js  (C 소유)
export function mountCropper(container, { onCrop });
//   container: HTMLElement.  붙여넣기(Ctrl+V)·드래그앤드롭·파일선택을 모두 받는다.
//   onCrop(blob, meta): 사용자가 영역을 확정할 때마다 호출. meta = {full: Blob} 원본도 준다.
//   크롭을 건너뛰면 원본 전체를 그대로 onCrop 에 준다.

// web/ocr.js  (O 소유)
export async function readLabels(blob);
//   -> { names: string[], formula: string|null, smiles: string|null }
//   names 는 영문 우선, 없으면 한글. 못 찾으면 빈 배열. 절대 예외를 던지지 않는다.
```

```
POST /api/check          (S 소유)   multipart/form-data: image, name
-> 200 application/json
{
  "verdict": "match" | "mismatch" | "unreadable",
  "grade":   "strong" | "weak" | null,        // 인식기 둘 합의=strong, 하나뿐=weak
  "reference": {"name","smiles","inchikey","formula"} | null,
  "read":      {"smiles","inchikey","heavy_formula","engines":[{"engine","smiles","inchikey","confidence"}]},
  "reasons":   ["골격이 다릅니다", "중원자 조성 C9 vs C8"]
}
```
`verdict` 는 **둘**이다(match/mismatch). 읽지 못한 것은 판정이 아니라 `unreadable` 이고,
그때도 화면은 정본을 보여준다. 확신의 정도는 `grade` 로만 표현한다.

## 화면 원칙 (U)

1. **점진적 렌더.** 정본 카드는 0.5 초 안에 뜬다. 서버 결과는 나중에 채운다. 스피너로 화면을 덮지 않는다.
2. **복사 버튼은 정본에만 둔다.** 사용자가 올린 그림 쪽에는 복사를 두지 않는다 -
   틀린 구조가 슬라이드로 나가는 통로를 우리가 열면 안 된다. 정본 카드에는 출처(PubChem CID)를 박는다.
3. 정본 카드의 복사 대상 넷: **PNG**(클립보드 이미지) · **SVG**(다운로드) · **SMILES**(텍스트) · **InChIKey**(텍스트).
   SMILES 는 **RDKit canonical 로 통일**한다 - PubChem 원본과 다를 수 있으므로 한쪽으로 고정한다.
4. `unreadable` 이어도 빈 화면이 아니다: "그림을 확실히 읽지 못했습니다. 요청하신 구조는 이것입니다 - 나란히 놓고 보십시오."
5. 이름을 못 찾으면 `compounds.js` 423 개에서 **편집거리 근접 제안**("Coffeine → Caffeine 을 찾으시나요?").
   **자동 선택 금지** - 사용자가 클릭해야 한다. 이건 입력 보정이지 판정이 아니다.

## 오늘 범위 밖 — 건드리지 않는다

입체화학 판정 · 세 번째 엔진 · 자동 분할기 · guard()/MCP · 신규 분자 변환 · 90 장 코퍼스.

## 근거 (docs/DIRECTION.md 실측 6·7)

- 슬라이드를 통째로 인식기에 먹이면 쓰레기가 나온다(탄소 100 개 폴리인, 신뢰도 0.793).
  그래서 **크롭은 오류 경로가 아니라 정상 흐름**이다.
- 이미지 안 텍스트는 6/6 정확했고 그림은 4 장 중 1 장만 정확했다.
  그래서 **텍스트가 정답이고 그림이 용의자**다.

# 개정 1 — 심사가 URL 배포다 (2026-09-09 23:35, 사용자 확정)

심사위원이 직접 접속해서 쓴다. **3GB 엔진을 상주시킬 곳이 없다.**

## 접는 것

**S(서버) 트랙을 만들지 않는다.** `/api/check` 도 없다. OCSR 은 요청 경로에서 빠진다.
`check --name`(MVP2 가 만드는 중)은 계속 만든다 - 그건 **로컬 CLI** 로 남고, README 의
"야생에서 잡은 오류" 기록을 만드는 데 쓴다. 웹 제품에는 들어가지 않는다.

## 그래서 입력이 셋이 된다 — 검출은 살아 있다

    이름 입력      → 정본 구조 + 복사                        예방
    SMILES 입력    → 이름과 InChIKey 대조 → 🔴/🟢            검출. 브라우저에서 완결
    이미지 붙여넣기 → OCR 로 이름·화학식·SMILES 를 뽑아 위 둘로 흘려보낸다

**핵심**: LLM 이 그린 이미지에 SMILES 가 인쇄돼 있으면(오늘 GPT 가 그랬다) 그것을 뽑아
검증할 수 있다. **SMILES 가 곧 구조이므로 이것이 진짜 검출이다** - OCSR 이 필요 없다.

이 경로는 이미 있다. B 가 만든 페이지가 이름/SMILES 둘 다 받고 InChIKey 로 대조한다.
남은 일은 **이미지에서 그 값들을 뽑아 입력칸에 채워 넣는 것**이다.

## 정직하게 말할 한계 — README 와 화면에 적는다

이미지에 SMILES 가 없고 텍스트가 전부 맞는데 **그림만 틀린 경우**(오늘 Gemini 카페인이 그랬다),
웹에서는 잡지 못한다. 그림을 읽어야 하고 그건 OCSR 이다.

그때 화면은 이렇게 말한다:

> 이 이미지는 SMILES 를 적어두지 않았습니다. 텍스트끼리는 일관됩니다(이름·화학식·IUPAC명).
> **그림 자체는 확인하지 못했습니다** — 정본을 나란히 놓았으니 비교해 보십시오.
> 그림까지 검사하려면 로컬 CLI 가 필요합니다.

"검사했습니다" 라고 말하지 않는다. 이 프로젝트가 PWP 를 비판한 근거가 그것이었다.

## 우선순위가 바뀐다

| | 전 | 후 |
|---|---|---|
| S 서버 | 필수 | **취소** |
| O OCR | 나중 | **핵심 경로** - 이미지 입력이 이것 없이는 아무것도 못 한다 |
| U 화면 | 입력 둘 | **입력 셋**, 판정 로직도 브라우저 |
| C 크롭 | 인식기용 | **OCR 용** - 텍스트 영역을 잘라 정확도를 올린다 |

C 의 크롭은 여전히 값이 있다. 다만 목적이 "인식기에 깨끗한 구조를 주는 것"에서
"OCR 에 깨끗한 텍스트를 주는 것"으로 바뀐다. 인터페이스(`mountCropper`)는 그대로다.

## 개정 2 — OCR 은 이름만. 입력은 한 칸 (23:45, grill 6)

**내가 개정 1 에서 SMILES 추출을 O 의 핵심이라 한 것은 틀렸다.** OCR 은 셋이 아니라 하나다.

| 뽑는 것 | 되나 | 왜 |
|---|---|---|
| 이름 | **된다** | 사전이 있다 - `compounds.js` 423 개 + 편집거리. "Coffeine" 도 복구된다 |
| 화학식 | 어렵고, **쓸 데가 없다** | 아래첨자가 깨진다. 게다가 대조 상대(그림에서 센 원자 수)가 웹에 없다 - OCSR 이 필요한데 접었다 |
| SMILES | **거의 안 된다** | 사전이 없어 보정 불가. 모든 문자가 의미(O/0, 1/l/I, `([=#@`), 대소문자가 분자를 바꾼다(c/C). 한 글자 오독률 1% 여도 40 자면 온전할 확률 67% |

게다가 이미지에 SMILES 가 인쇄됐으면 **같은 대화 텍스트에도 있다.** 사용자가 복사하면 된다.

`readLabels` 시그니처는 동결이므로 유지하되 `formula`·`smiles` 는 `null` 로 둔다.

### OCR 은 임계 경로가 아니다

    이미지 -> [OCR 이 이름 칸을 채운다]   성공하면 편하고
                    v
              [이름 입력칸]              실패해도 사용자가 친다 (3 초)
                    v
              정본 + 판정

심사위원이 직접 쓰는 URL 이므로 **OCR 실패가 "이 사이트 안 되네" 가 되면 안 된다.**

### 입력 칸은 하나다

"화합물 이름 또는 SMILES 를 붙여넣으세요" 한 칸. RDKit.js 로 파싱해보고 되면 SMILES,
안 되면 이름으로 조회한다. **판별이 규칙이라 추론이 아니다.** 칸이 셋이면 심사위원이
어디에 뭘 넣을지 고민한다. 이미지 붙여넣기는 그 칸 위의 별도 영역.

### "야생에서 잡은 오류" 섹션을 화면에 박는다

웹에서 재현되지 않는 것을 버리면 심사위원은 이걸 **이름 조회 사이트**로 본다.
오늘 실제로 잡은 것을 화면 한구석에 남긴다 - Gemini 카페인 이미지, 두 InChIKey,
탄소 8 대 9, 그리고 그 이미지가 **자기가 인쇄한 화학식과도 안 맞았다**는 사실.

> 웹이 못 하는 것을 정직하게 보여주는 것이 웹이 하는 것의 값을 올린다.

### 열어둔 것 — Hugging Face Spaces

무료 티어 RAM 이 충분하거나 DECIMER 공개 Space 를 API 로 부를 수 있으면 검출이 웹에서
살아난다. 확인 중이다. **지금 트랙을 되돌리지 않는다** - U·C·O 는 어느 쪽이든 필요하다.
결과가 "가능" 이면 그때 30 분 스파이크로 붙일지 정한다.
