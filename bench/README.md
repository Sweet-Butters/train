# bench — chemcheck 평가 장치

숫자를 담아두는 곳이 아니라 숫자를 뽑는 장치다.

## recognize 평가 — "정확한 SMILES 를 준다" 를 숫자로 (결정 2, 오늘의 제품)

```bash
python -m bench.run --task recognize --engine oracle      # 완벽한 인식기 둘 - 장치 점검
python -m bench.run --task recognize --engine shaky       # 흔들리는 인식기 하나
python -m bench.run --task recognize --engine colluding   # 둘이 같은 방향으로 틀림 -> exit 1
python -m bench.run --task recognize --engine none        # 바닥값 - 전부 물러남
bash bench/gate_recognize.sh --detail                     # 실제 인식기. 하루 끝 한 번, 게이트로
```

**세트.** 알려진 분자 50개(`bench/molecules.py`)를 RDKit 으로 그린다. 렌더 변주 8종
(`bench/variants.py`: 크기·선 굵기·글꼴·회전·잡음·JPG 압축)을 장 번호로 돌려 붙여
변주마다 6~7장이 든다. 정답 InChIKey 는 이름이 아니라 SMILES 에서 계산한다 - 라벨을
믿지 않는다는 원칙 그대로다. 슬라이드·덱·`NOT_A_STRUCTURE` 는 여기 없다.

**채점.** 인식은 한 번만 하고 규칙을 둘 적용한다 (`bench/recog.py`).

| 팔 | 규칙 | 뜻 |
|---|---|---|
| 합의 게이트 | 인식기 **종류** 둘 이상이 골격(InChIKey 앞 14자)에 합의해야 답 | `recognize` 가 쓰는 규칙 |
| 신뢰도 게이트 | 인식기 하나라도 신뢰도 ≥0.8 이면 그 답. 신뢰도 없는 인식기는 그대로 믿음 | `verdict.py` 의 단독 경로 = LLM 이 답하는 방식 |

장마다 결과는 셋 중 하나다: **자신 있게 틀림**(답을 냈는데 골격이 다름) · 정확(답을
냈고 골격이 맞음, 입체까지 맞은 수는 따로) · 물러남(확신 없음으로 뺌, 그중 정답을 낸
인식기가 있던 수는 따로). 엔진별 표는 인식기 하나만 믿었을 때의 성적이고 마지막 열
'고신뢰(≥0.8) 틀림' 이 LLM 의 실패 그 자체다. 변주별 표는 어느 변주가 유독 깨지는지
가리킨다.

**리포트 첫 줄은 '자신 있게 틀림' 이다.** 정확도가 먼저 오면 리포트가 스스로를 속인다 -
물러나기만 하는 도구는 자신 있게 틀림 0% 를 공짜로 얻으므로 물러남을 바로 밑에 둔다.
합의 게이트 팔에서 자신 있게 틀림이 1건이라도 나오면 exit 1 로 끝난다.

**스텁으로 장치를 검증한 결과** (성능이 아니다):

| 스텁 | 합의 게이트 | 신뢰도 게이트 |
|---|---|---|
| oracle 둘 | 정확 50/50 · 자신 있게 틀림 0 | 같음 |
| shaky 혼자 (3장마다 신뢰도 0.93 으로 엉뚱한 골격) | 물러남 50/50 (정답 있던 것 35) · 틀림 0 | **자신 있게 틀림 15/50** |
| colluding 둘 (같은 장에서 같이 틀림) | **자신 있게 틀림 15/50 → exit 1** | 같음 |
| 없음 | 물러남 50/50 | 같음 |

shaky 한 줄이 이 장치의 존재 이유다. 인식기 하나의 자신감은 답이 아니다.

**실행 경로.** `--engine real` 은 `chemcheck.ocsr.load_engines()` 를 그대로 쓴다. 인식기
환경(`.venv310`·`models/`)은 `D:/orca/workspaces/train/chemcheck` 에만 있으므로
`CHEMCHECK_ROOT` 로 그 워크트리를 가리키면 chemcheck 패키지와 모델은 거기서, bench 는
이 워크트리에서 가져온다. `bench/gate_recognize.sh` 가 그 조합을 절대경로로 적어 두었고
`heavy_gate.sh` 를 지나 돈다. 리포트는 `bench/decks/recognize_set/report_*.txt` 에 남는다.

## 실측 기록 5 — recognize 50장, 실제 인식기 둘 (2026-09-09)

`bench/results/recognize_50_20260909.{json,txt}`. 인식 결과 원문은 JSON 이고
`python -m bench.run --task recognize --replay bench/results/recognize_50_20260909.json --detail`
로 리포트를 다시 뽑는다. 인식기 MolScribe(.venv310 워커) + DECIMER, 장당 약 30초.

숫자를 보기 전에 적은 성공 기준: 합성 렌더 50장에서 자신 있게 틀림 0건 = 상한 오탐률
약 6% 이하 (95% 신뢰). 실제 그림에 대해선 아무 말도 아니다.

    [합의 게이트]    자신 있게 틀림  0/50   정확도 44/50 (입체까지 44)   물러남 6/50
    [신뢰도 게이트]  자신 있게 틀림  2/50   정확도 43/50                물러남 5/50 (전부 신뢰도 부족)

**담합 0장.** 둘 다 답한 50장 중 같이 틀린 장이 없다. 합의 게이트가 틀린 답을 통과시킨
경우가 없고, 결정 3 의 사망 기준 세 줄 어디에도 걸린 건이 없다. 물러난 6장은 전부
한 엔진만 틀렸다 - 세 번째 독립 신호가 있으면 6장 모두 회수 가능한 상한이다.

| 물러난 장 | 변주 | 틀린 엔진 | 읽은 것 |
|---|---|---|---|
| 2 아세트산 | large | MolScribe 0.68 | `CC(C)O.O` |
| 6 L-젖산 | serif | MolScribe 0.80 | `C#CC(=O)O` |
| 9 톨루엔 | plain | DECIMER | `C1=CC=C(C=C1)C(F)(F)F` (메틸을 CF3 로) |
| 13 퓨란 | rotated | MolScribe 0.80 | `C1=COCC1` (이중결합 하나 빠짐) |
| 14 싸이오펜 | serif | MolScribe 0.70 | `C1CCSCC1` |
| 46 페니실린 G | serif | DECIMER | 이중고리 골격 오독 |

**변주.** serif 가 6장 중 3장 물러남으로 유독 약하다. MolScribe 2, DECIMER 1 이라
한 엔진만의 약점은 아니다. 나머지 변주는 0~1장.

**신뢰도 문턱(0.8)은 이 세트에서 해롭다.** 합의한 44장 중 3장(아세톤 small 0.72,
신남알데하이드 noisy 0.74, 모르핀 jpeg 0.75)은 정답인데 신뢰도가 0.8 미만이다 - 합의 팔에
문턱을 얹었다면 정답 3건을 버렸을 것이다. 판별력도 없다: MolScribe 정답 신뢰도 0.72~0.92,
오답 0.68~0.80 으로 겹친다. 오답 4건 중 2건이 정확히 0.80 이라 문턱을 통과한다.
0.85 로 올리면 오답 4건은 전부 걸리지만 정답 11건도 같이 걸린다. **문턱이 아니라 합의가
일을 한다** - 기준선 팔이 자신 있게 틀린 2건은 둘 다 합의 팔에서 물러남으로 잡혔다.

엔진별: DECIMER 48/50 골격 정답(입체까지 44 - 입체를 4장 놓침), MolScribe 46/50(입체 46).
서로 다른 장에서 틀린다.

이 숫자는 RDKit 이 그린 그림의 상한이다. 스크린샷·손그림·교재 스캔에 대해서는 아무 말도
하지 않는다.

## 덱 판정 평가 (결정 2 이후 보류)

슬라이드에서 이름과 그림을 짝지어 판정하는 경로의 장치다. 아래는 그때의 기록이다.

```bash
python -m bench.run --engine oracle          # 장치 점검 (오늘 돌아간다)
python -m bench.run --engine hallucinating   # 구조식 아닌 그림에도 답하는 인식기
python -m bench.run --engine none            # 바닥값 - 전부 침묵해야 한다
python -m bench.run --engine real            # A 착지 후 진짜 숫자

# 실제 자료 + 사람이 붙인 라벨 (자료는 저장소에 없다 - 로컬 경로로 준다)
python -m bench.run --manifest bench/decks/hydrocarbons_11c13.json                     --deck "<로컬>/11C13 PPT.pptx" --detail
```

## 리포트가 판정률부터 시작하는 이유

침묵하는 검사기는 만들기 쉽다. 항상 판정불가를 내면 오탐률 0% 짜리 완벽한 도구가
되고, 동시에 완전히 쓸모없다. `--engine none` 이 정확히 그 상태를 보여준다 —
판정률 0%, 오탐률 0%. 판정률을 첫 줄에 두지 않은 리포트는 스스로를 속인다.

## 두 팔로 재는 이유

| 팔 | 판정기 |
|---|---|
| `chemcheck` | `verdict.judge` — 신뢰도 게이트 + 엔진 합의 + 골격/입체 구분 |
| `baseline` | `baseline.naive_judge` — 보류 없음. 예측 하나를 참조 하나와 대조 |

둘은 **같은 인식 결과**를 본다 (인식기는 한 번만 돈다). 차이는 판정 규칙뿐이므로,
두 성적의 차이가 곧 chemcheck 이 부품 위에 얹은 것의 크기다.

## 라벨을 믿지 않는다

`validate` 가 각 케이스의 라벨을 PubChem + RDKit 으로 다시 계산해 대조한다.
(이름, 그려진 SMILES) 의 참 관계는 OCSR 없이 계산되기 때문이다. 선언과 계산이
어긋나면 도구가 아니라 케이스가 틀린 것이다.

라벨이 틀린 채로 잰 오탐률은 오탐률이 아니다.

## 알려진 한계

- **합성 코퍼스는 렌더러가 하나다.** `CORPUS` 의 그림은 전부 RDKit 이 그렸다.
  실제 슬라이드는 ChemDraw 내보내기·스크린샷·손그림이 섞이고 해상도도 제각각이다.
  여기서 나온 숫자는 OCSR 성능의 **상한**이지 현장 성능이 아니다.
- **`decks/` 가 비어 있다.** 현장 숫자는 라벨을 손으로 붙인 실제 강의자료에서 나온다.
  이게 채워지기 전까지 이 장치는 자기 자신만 검증한다.
- **케이스가 9건이다.** 비율을 말할 크기가 아니다. 지금은 장치가 도는지 보는 용도다.

## 실측 기록 1 — 실제 강의자료 (2026-09-09)

자료: 고분자 합성 메커니즘 강의 덱, 8장, PDF. Gemini Notebook 이 생성한 한국어 자료.
저작물이므로 저장소에 두지 않는다. 제자리에서 읽었다.

    그림 8건 중 0건을 판정했습니다  (판정률 0.0%)
      [판정불가]  8   그림 옆에 이름이 없음

판정률 0%. 이유가 셋이고 깊이가 다르다.

**1. 텍스트 레이어가 없다.** PDF 전체에 0자. pdfminer.six 와 pypdfium2 로 각각
독립 확인했으므로 우리 추출 경로의 버그가 아니다. 페이지가 5121x2880px 통짜
래스터다 - 이름이 픽셀 안에 있어 기계가 읽을 수 없다.

**2. '그림'이 슬라이드 전체다.** 추출된 이미지는 구조도가 아니라 슬라이드 한 장
통째다. OCSR 에 먹여도 제목·본문·여러 구조가 섞인 그림이라 의미가 없다.

**3. 구조가 일반식이다.** 3장은 디이소시아네이트(OCN-R-NCO) + 디올(HO-R'-OH)
-> 폴리우레탄이고, 6장은 라디칼 중합과 개환 중합의 반응 도식이다. R, R' 는
InChIKey 로 표현할 수 없고, 반응 도식은 단일 화합물이 아니다.

1 과 2 는 입력 형식 문제라 고칠 수 있다 (원본 PPTX, 또는 OCR + 구조 검출).
**3 은 다르다 - 이 자료에는 검사할 대상이 애초에 없다.** chemcheck 은 '한 장에
화합물 이름 하나와 그 구조 그림 하나'를 전제하는데, 이 덱은 반응 메커니즘과
개념 도해로 되어 있다.

덱 하나다. 일반화하면 안 된다. 다만 처음 만난 실제 자료가 전제에 맞지 않았다는
사실 자체가 정보다. 다음 자료는 **개별 화합물의 이름과 구조가 함께 나오는**
것이어야 이 장치가 잴 것이 생긴다 - 유기화학 강의자료가 그런 형태다.

곁들여: 이 덱은 AI 가 생성한 자료다. chemcheck 의 표적 그 자체인데,
평면 이미지라 chemcheck 이 보지 못한다.

## 실측 기록 2 — 그림의 대부분은 구조식이 아니다 (2026-09-09)

자료: 탄화수소 강의 덱, 398장 PPTX. 텍스트 100%, 그림과 글자가 함께 있는 장 167장.
형태는 chemcheck 의 전제에 맞는다. 그런데 그림 쪽이 다르다.

    그림 총계     371
    고유 그림     109      <- 304 건이 중복
    최다 반복      46 번    <- 구조식은 46 번 반복되지 않는다

표본 12개를 눈으로 확인했다. 화학 구조식은 2~3개뿐이었다. 나머지는 아인슈타인
캐리커처, 오비탈 도해, 비커 그림, 플라스틱 용기 사진, 소스병 사진, 검은 사각형.
`extract.py` 의 필터는 크기뿐이고 '이게 구조식인가'는 아무도 묻지 않는다.

**이것이 실제 자료의 지배적 오탐원일 수 있다.** OCSR 은 무엇을 주든 SMILES 를
낸다. 클립아트에서 읽은 SMILES 가 슬라이드의 이름과 다르면 '오류'가 되는데,
자료는 멀쩡하다.

그래서 `Truth.NOT_A_STRUCTURE` 를 넣고 `--engine hallucinating` 으로 재봤다.
구조식은 제대로 읽고 구조식이 아닌 그림에도 신뢰도 0.95 로 답하는 인식기다.

    [chemcheck]   오탐률 22.2% (2/9)   물러남 0.0% (0/3)
    [baseline]    오탐률 33.3% (3/9)   물러남 0.0% (0/3)

**인식기 하나로는 chemcheck 의 방어가 버티지 못한다.** 신뢰도 게이트(0.80)는
0.95 를 통과시키고, 합의 게이트는 엔진이 하나면 언제나 합의한다. 보류 규칙이
오탐을 3건에서 2건으로 줄였을 뿐이다.

이것이 다중 엔진 합의가 선택이 아니라 필수인 이유다. 엔진이 둘이고 서로 다른
답을 내면 그때 비로소 보류된다. **A 가 두 인식기를 함께 세우는 일은 정확도
문제가 아니라 오탐 문제였다.**

### 판정률의 분모를 바꿨다

구조식이 아닌 그림에 물러난 것은 잘한 일이지 못 본 것이 아니다. 그것을 분모에
넣으면 옳게 행동한 데 벌점을 매기게 된다. 판정률의 분모는 이제 '판정했어야 할
케이스'다. 대신 분모를 우리가 정하게 되므로 조작 여지가 생긴다 -
`NOT_A_STRUCTURE` 라벨은 사람이 눈으로 붙이고, `validate` 가 근거(note) 없는
선언을 거부한다.

## 실측 기록 3 — 전제는 성립한다. 오탐이 날 자리도 나왔다 (2026-09-09)

탄화수소 강의 덱 398장을 인식기 없이 끝까지 돌렸다. 인식기가 없으므로 판정은
전부 보류지만, 보류 사유의 갈래가 전제를 재준다.

    전체 장                 398
    그림이 있는 장          167
    이름이 잡힌 장          296
    그림+이름 둘 다 있는 장 128     <- 판정 후보 장
    그 장들의 그림          279 건   <- 전체 371 건의 75%

    [판정불가] 371
           278  인식기를 쓸 수 없음    <- 이름은 잡혔다. A 만 오면 판정된다
            93  그림 옆에 이름이 없음  <- 전제가 안 맞는 장

**전제는 성립한다.** '슬라이드에는 이름과 그림이 함께 있다'가 실제 자료에서
그림 기준 75% 로 지켜졌다. 첫 자료(고분자 PDF)에서 0% 였던 것과 대비된다 -
그쪽은 텍스트 레이어가 없었다.

### 그런데 '이름이 잡혔다'가 '화합물 이름이 잡혔다'는 아니다

해석된 고유 이름 168종 중 상위:

    47 Alkenes    41 Benzene   22 Ethane     18 Ethyne    17 Platinum
    14 Sol        12 PSV       12 Palladium  9 Challenge  6 ene   6 Suffix

`Alkenes` 는 분류명이고 `Sol`·`PSV`·`Challenge`·`ene`·`Suffix` 는 화합물이
아니다. PubChem 은 분류명과 상표명을 정식으로 들고 있어서 해석해 준다
(`Challenge` 는 제초제 상표명, `Sol` 은 당의 동의어).

**판정 후보 장 128개 중 24개(그림 77건, 후보의 28%)는 잡힌 참조가 전부
분류명이거나 잡음이었다.** 대부분 `Alkenes` 하나뿐이다. 그 장들의 그림은 맞게
그려진 특정 알켄인데, 참조는 분류명이다. 인식기가 오면 여기서 '오류'가 난다 -
자료는 멀쩡한데.

그리고 후보 장 128개 중 77개는 **참조가 하나뿐이다.** '참조 3개 중 하나라도
맞으면 통과'라는 방어는 참조가 하나이고 그것이 틀렸을 때 아무것도 하지 못한다.

### 코퍼스에 반영한 것과 남긴 것

반영: 진짜 이름 옆에 분류명·잡음이 함께 있는 장 2건. 오라클로는 통과한다 -
참조 예산 안에 진짜 이름이 함께 들어오면 방어가 작동한다.

남긴 것: **진짜 이름이 아예 없고 분류명만 있는 장.** 이건 '그림이 틀렸다'가
아니라 '검사할 주장이 없다'에 가깝다. 슬라이드가 특정 화합물을 지목하지 않았는데
도구가 지목했다고 치고 대조하는 것이다. 라벨 체계를 하나 더 두어야 할 수도
있는데(구조식이 아님과 짝을 이루는 '주장이 없음'), 그 전에 이름 해석 쪽에서
분류명을 걸러내는 편이 옳은지 코디네이터·C 와 정할 일이다.

## 실측 기록 4 — 라벨 붙인 실제 덱. 완벽한 인식기로도 오탐 12.5% (2026-09-09)

탄화수소 덱의 판정 후보 그림 중 고유한 것 32개에 사람이 라벨을 붙였다
(`bench/decks/hydrocarbons_11c13.json`). 자료는 저작물이라 담지 않고 라벨만 담는다.
인식기는 라벨에서 답을 읽는 오라클이다 - **그러므로 아래 오탐은 인식기 탓이 아니다.**

    [chemcheck]  판정률 100.0% (8/8)   오탐률 12.5% (4/32)   물러남 95.8% (23/24)
    [baseline]   판정률 100.0% (8/8)   오탐률 18.8% (6/32)   물러남 95.8% (23/24)

라벨 구성: 구조식이 아닌 그림 23, 같은 분자 8, 주장 없음 1.
**후보 그림의 72% 가 구조식이 아니었다** - 클립아트, 사진, 궤도 도해, 쐐기 기호 조각.

### 오탐 4건의 원인 (전부 인식기 밖)

세 건은 **참조 예산**이다. `pipeline.py` 의 `MAX_REFERENCES_PER_SLIDE = 3`.

    p26  헥세인            슬라이드 원문에 'Hexane' 이 있는데 참조 3칸에서 밀렸다
    p26  2,2-다이메틸뷰테인  원문에 있는데 밀렸다
    p154 사이클로뷰테인      원문에 'Cyclobutane' 이 있는데 밀렸다

p26 은 헥세인의 이성질체 5개를 한 장에 늘어놓고 다섯 이름을 모두 적어둔 장이다.
자료는 완벽하다. 도구가 이름을 셋만 보고 나머지 둘의 그림을 '오류'라 했다.
**이름이 여럿인 장에서 참조 예산이 곧 오탐률이 된다.**

한 건은 **이름 잡음**이다.

    p170 헥사트라이엔  슬라이드는 화합물 이름을 대지 않는다 ('이 화합물에서 기하이성질을
                      보이는 이중결합 수를 찾아라'). 잡힌 참조는 'Sol'(당의 동의어)뿐이고
                      그것과 대조해 '오류'라 했다.

### 여기서 나온 라벨 하나

`Truth.NO_CLAIM` - 구조식은 맞지만 슬라이드가 화합물을 지목하지 않은 경우.
`NOT_A_STRUCTURE` 와 짝이다. 하나는 그림 쪽에 검사 대상이 없고 다른 하나는 이름
쪽에 검사할 주장이 없다. 둘 다 물러나는 것이 정답이므로 채점에서 같이 다룬다.

### 이 숫자를 어떻게 읽어야 하나

오탐률 12.5% 는 **바닥값**이다. 인식기가 완벽하다고 가정했는데도 이만큼 난다.
진짜 인식기가 오면 여기에 인식 오류가 더해진다. 그리고 이 오탐들은 인식기를
아무리 잘 만들어도 줄지 않는다 - 참조 예산과 이름 해석에서 나오기 때문이다.

보류 규칙은 오탐을 6건에서 4건으로 줄였고 판정은 한 건도 포기하지 않았다.
값어치는 있으나, 남은 4건은 보류 규칙이 닿지 않는 곳에서 난다.

## 사진이 안 읽히는 진짜 원인 - 화질이 아니라 **구조가 화면에서 차지하는 비율** (2026-09-10)

사용자 카메라 사진이 계속 쓰레기(`*` 31 개 + `[CH3]` 조각 9 개)를 내서, 조건을
하나씩 바꿔가며 배포된 엔드포인트로 재봤다.

**화질은 원인이 아니었다 - 7/7 전부 정확했다.**

| 조건 | 두 엔진 결과 |
|---|---|
| 원본 · 3배 확대 JPEG · 조명 기울기 · 3.5도 기울임 · 가우시안 블러 2.2 · 센서 잡음 · 전부 합친 것 | **7/7 모두 RYYVLZVUVIJVGH 정확, `*` 0, 조각 1** |

주변에 글자를 넣거나 여백을 늘려도 통과했다. 표 선을 그렸을 때만 MolScribe 가
한 번 깨졌고 DECIMER 는 맞혔다.

**깨뜨린 것은 구조의 상대적 크기였다.** 같은 그림을 프레임 비율만 바꿔 재면:

| 구조가 화면의 | MolScribe | DECIMER |
|---|---|---|
| 85% | 정확 | 정확 |
| 50% | **13 조각** (`[C-]#[C-]` 반복) | 정확 |
| 30% | 3 조각 | 정확 |
| 18% | **`*` 7 개 + 5 조각** (`*N.*N.*N.*N*N.*n1cnc(=O)n1*`) | 틀림 |

18% 줄이 사용자가 본 것과 같은 패턴이다. 그리고 그렇게 되는 이유는 자르기의
기본 선택 영역이 **이미지 전체**였기 때문이다 - 드래그하지 않고 확인만 누르면
사진이 통째로 간다. 페이지나 화면을 찍으면 구조는 10~20% 뿐이다.

**대응**: 기본 선택을 가운데 60% 로 좁히고, 85% 넘게 선택한 채 확인하면
"구조만 크게 잘라 주세요" 를 띄운다. 부수적으로 알게 된 것 - **DECIMER 가
작은 구조에 훨씬 강건하다**(30% 까지 정확). MolScribe 는 50% 에서 이미 깨진다.
